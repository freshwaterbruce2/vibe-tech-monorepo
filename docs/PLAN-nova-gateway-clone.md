# Implementation Plan: Nova Agent Gateway Clone (Open-Claw Replacement)

This document outlines the design, architecture, and step-by-step development roadmap for the **Nova Agent Gateway** (`apps/nova-gateway`), a custom, 24/7-runnable gateway service designed to replace OpenClaw. It enables Telegram, Discord, and future WhatsApp integrations to connect securely to the desktop-based Nova Agent.

---

## 1. Overview & Architecture

The Nova Agent Gateway functions as an event-driven messaging broker. It runs continuously on a VPS or server, receives user messages from chat networks, resolves platform-specific users to a unified customer profile, and forwards those events as serialized execution requests to the desktop-bound Nova Agent over a secure WebSocket IPC tunnel.

### Architectural Subsystems

1. **Modular Platform Adapters (`src/adapters/`)**
   - Implements a unified `BaseAdapter` interface.
   - Handled via `telegraf` (Telegram) and `discord.js` (Discord) in the initial phase.
   - Designed with clear hooks and event signatures so that a WhatsApp adapter (using Baileys or Puppeteer) can plug in later without modifying core session or message-routing code.

2. **Unified Session Manager (`src/core/session-manager.ts`)**
   - Keeps individual platform channel contexts separate by default.
   - Integrates a SQLite-backed mapping schema that links different platform-specific identifiers (e.g., Telegram `chat_id` and Discord `user_id`) to a single **Unified Client ID**.
   - Syncs conversation logs, project mappings, preferences, and active workspaces across platforms.

3. **IPC Tunnel Client (`src/core/ipc-client.ts`)**
   - Connects to the local/desktop `ipc-bridge` service running on port `5004`.
   - Supports outgoing secure WebSocket connections (`wss://` or authenticated `ws://`) using `x-bridge-secret` authentication tokens.
   - Handles reconnection logic with exponential backoff and message caching during offline periods.

4. **Command & NLP Router (`src/core/command-router.ts`)**
   - Inspects incoming messages to differentiate between:
     - **Slash Commands**: Parses leading slashes (e.g., `/status`, `/screenshot`, `/mcp`) and dispatches them to immediate execution routines.
     - **Natural Language Routing**: Wraps text messages into `agent:task:dispatch` payloads and routes them to Nova's reasoning engine via the IPC tunnel.

## 2. Success Criteria

### Functional Uptime & Execution
- **Persistent VPS Uptime**: The gateway runs 24/7 on a VPS, establishing and maintaining a persistent, authenticated WebSocket link to the desktop Nova Agent's IPC Bridge.
- **Platform Agnosticism**: Telegram and Discord clients receive real-time, asynchronous responses generated by the desktop Nova Agent.
- **Direct Slash Commands**:
  - `/status`: Queries desktop CPU, memory, and Nova Agent task queues, returning formatted stats.
  - `/screenshot`: Triggers desktop screen capture and returns the PNG image to the chatting client.
  - `/mcp <server> <tool> <args>`: Runs desktop-bound Model Context Protocol tools directly from the chat client.
- **Cross-Platform Session Sync**: Linking a Discord account and a Telegram account to a single Client ID merges their contextual chat history and shared active variables.
- **Graceful Fault Tolerance**: Returning user-friendly alerts when the desktop Nova Agent is offline (e.g. `"Desktop agent is unreachable. Queuing message..."`) instead of dropping the connection.

### Non-Functional & Workspace Constraints
- **Strict Data Isolation**:
  - Zero read/write operations to the `C:\dev` codebase folder or `/tmp` at runtime.
  - SQLite database saved strictly to `D:\databases\nova-gateway.db` in WAL mode.
  - Runtime log files saved strictly to `D:\logs\nova-gateway\nova-gateway.log`.
- **Modularity & Maintainability**:
  - Every source code file remains strictly under the **500-line soft limit**.
  - 100% strict TypeScript typing: no usage of implicit `any` without a documented justification.
- **Vitest & Nx Compliance**:
  - Fully integrated with the workspace Nx project structure (`pnpm nx test nova-gateway`).
  - Unit tests achieve at least 85% line coverage.

## 3. Tech Stack

- **Runtime & Version Manager**: Node.js v22.x, managed via `pnpm 10.28.2+` workspace corepack.
- **HTTP Server**: Fastify v5.x with `@fastify/websocket` for log streaming and webhook integration.
- **Database**: `better-sqlite3` configured with WAL (Write-Ahead Logging) for lightweight database persistence.
- **Client Libraries**:
  - `telegraf` v4.16.x (Telegram Bot integration).
  - `discord.js` v14.16.x (Discord API integration).
- **Validation**: `zod` for validating environment configurations and incoming payload boundaries.
- **Logging**: Custom JSON logger built on top of `@vibetech/logger` writing directly to `D:\logs\nova-gateway\`.
- **Testing**: `vitest` with mock-based tests, utilizing standard monorepo setups.

## 5. Task Breakdown

### Task 1: Scaffold the Nx Application
- **INPUT**: Workspace template structure and package definitions.
- **OUTPUT**: Scaffolding configuration files in `C:\dev\apps\nova-gateway/`:
  - `project.json` configuring targets: `build` (via tsup/vite), `lint` (via Biome/ESLint), `test` (via Vitest), and `typecheck`.
  - `package.json` specifying dependencies (`fastify`, `telegraf`, `discord.js`, `better-sqlite3`, `zod`).
  - TS configs (`tsconfig.json`, `tsconfig.app.json`, `tsconfig.spec.json`).
  - `.env.example` file documenting required keys.
- **VERIFY**:
  - Run `pnpm nx show projects` and ensure `nova-gateway` is registered.
  - Run `pnpm nx run nova-gateway:typecheck` to confirm compiler initialization.

---

### Task 2: Config Validation & Path Enforcement
- **INPUT**: Environment variable specifications (`PORT`, `DATABASE_URL`, `LOG_DIR`, token keys).
- **OUTPUT**: `src/config/env.ts` verifying environments via Zod.
  - Enforces `D:\databases\nova-gateway.db` as the only allowed database path.
  - Enforces `D:\logs\nova-gateway\` as the only allowed log directory.
  - Fails application startup with explicit warnings if these paths point to `C:\` or temporary folders.
- **VERIFY**: Run `vitest tests/unit/env.test.ts` to test path verification schemas with both conforming and non-conforming parameters.

---

### Task 3: Database Mapping & Schema Implementation
- **INPUT**: SQLite connection client (`better-sqlite3`).
- **OUTPUT**:
  - `src/db/client.ts` setting up the database connection at the verified `D:\` path.
  - `src/db/schema.ts` defining relational structures:
    - Table `unified_clients` (id primary key, created_at).
    - Table `user_identities` (id, unified_client_id FK, platform, platform_user_id, platform_username) with a unique constraint on `(platform, platform_user_id)`.
    - Table `client_sessions` (unified_client_id FK, platform, last_channel_id, conversation_state, last_active).
- **VERIFY**: Instantiate the database client during tests, execute migrations, verify constraints, and write mock records. Confirm that WAL files (`-wal` and `-shm`) are generated on the `D:\` drive.

---

### Task 4: Unified Session Manager
- **INPUT**: Active incoming user messages and identity records.
- **OUTPUT**: `src/core/session-manager.ts` creating a manager class that:
  - Resolves a incoming platform user (`platform`, `platform_user_id`) to a `Unified Client ID`.
  - Links new platform identities (e.g., Telegram and Discord) to an existing unified profile when requested.
  - Stores and retrieves active conversation state and recent message histories across sessions.
- **VERIFY**: Unit test `tests/unit/session-manager.test.ts`. Verify that searching for a user on Telegram and a linked user on Discord yields the same `Unified Client ID` and shares state.

---

### Task 5: WebSocket IPC Tunnel Client
- **INPUT**: Outgoing WebSocket client framework, authorization bearer token.
- **OUTPUT**: `src/core/ipc-client.ts` implementing a client that:
  - Establishes a connection to the desktop Nova Agent `ipc-bridge` (`ws://localhost:5004` or remote secure `wss://`).
  - Sets appropriate auth headers (`Authorization: Bearer <secret>`).
  - Handles protocol message frames like `ping`/`pong` and routes incoming executions.
  - Implements an offline queue that buffers user prompts if the tunnel goes offline and pushes them once reconnected.
- **VERIFY**: Run unit tests mocking the `ipc-bridge` WebSocket server. Assert connection handshake, successful authentication, and automatic reconnection triggers.

---

### Task 6: Command Router & Slash Command Handler
- **INPUT**: User string input and command prefixes.
- **OUTPUT**: `src/core/command-router.ts` directing incoming user requests.
  - Matches string inputs starting with `/`.
  - Dispatches slash commands (`/status` requesting telemetry; `/screenshot` instructing desktop capture; `/mcp` invoking specified tools).
  - Routes plain text messages directly to the IPC client as `agent:task:dispatch` payloads.
- **VERIFY**: Run unit tests validating different patterns of input texts (e.g., `/status`, `/mcp mockServer mockTool`, and generic conversations) and assert correct routing classification.

---

### Task 7: Telegram Bot Adapter
- **INPUT**: Telegram Token, webhook configuration.
- **OUTPUT**: `src/adapters/telegram.ts` executing the `Telegraf` SDK.
  - Registers commands (`/status`, `/screenshot`, `/mcp`, `/help`).
  - Listens to incoming chat messages and routes them through the session manager and command router.
  - Maps platform context back to standardized adapter responses.
- **VERIFY**: Run a mock verification suite feeding Telegram bot updates to the adapter and asserting correct outbound command routing.

---

### Task 8: Discord Bot Adapter
- **INPUT**: Discord Client secrets and gateway intent scopes.
- **OUTPUT**: `src/adapters/discord.ts` executing the `discord.js` client.
  - Supports mention-based triggers (`@NovaAgent`) and direct messages.
  - Employs typings controls (displays "typing..." while waiting for a response from the desktop agent).
  - Sanitizes markdown outputs to prevent leaking backend syntax.
- **VERIFY**: Mock Discord gateway messages and assert the adapter correctly listens to mentions and triggers typing states.

---

### Task 9: WhatsApp Modular Extension Point
- **INPUT**: Modular Adapter design specifications.
- **OUTPUT**: `src/adapters/whatsapp.ts` implementing the adapter interface but serving as an architectural stub.
  - Exposes hooks showing where Baileys or Puppeteer clients will connect.
  - Proves that adding a new messaging network requires zero refactoring of `session-manager.ts` or `command-router.ts`.
- **VERIFY**: Verify compile-time type conformance of the adapter stub under TS strict compilation.

---

### Task 10: Fastify Web Server & Webhook Routing
- **INPUT**: Web server configuration, route paths.
- **OUTPUT**: `src/server/app.ts` and `src/server/routes.ts`:
  - Registers `/health` reporting gateway performance and backend tunnel status.
  - Registers endpoint routes for Telegram/Discord webhooks to process serverless updates.
  - Integrates `/ws/logs` to broadcast debug events for administrators.
- **VERIFY**: Start the server locally using test configurations. Call `/health` via `curl` and verify it returns `200 OK` with JSON telemetry.
