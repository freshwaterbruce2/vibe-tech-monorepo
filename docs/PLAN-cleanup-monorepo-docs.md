## Overview
This plan outlines the systematic cleanup and standardization of documentation files across the entire VibeTech monorepo. It enforces the new rules established in [RULES.md](file:///C:/dev/docs/ai/RULES.md) to eliminate context clutter (historical point-in-time files in roots) and ensure that every application, package, MCP server, tool, and workflow has exactly its required canonical documents.

### Scope & Exclusions
* **Included**: Active monorepo projects registered in the workspace (configured in `WORKSPACE.json`) under `apps/`, `packages/`, and `tools/`.
* **Excluded**:
  - `apps/gravity-claw` (local-only nested WIP submodule).
  - Standalone apps in `C:\dev` (like `vibe-mechanic`).
  - Anything relating to `gravity claw` or `open claw` (e.g. `openclaw-bridge`, etc.).
  - Relaxed directories / temporary scratchpads (like `packages/games`).

### Archive Location
* **Single Centralized Archive**: All historical point-in-time documents (such as post-mortems, legacy reports, and temporary logs) will be moved to a single centralized archive folder under `C:\dev\docs\archive/<project-name>/`.
* **C: Drive Compliance**: Since these are version-controlled documentation files, they must remain on the `C:\dev` drive to satisfy canonical path rules.

### Document Skeleton & Dynamic Generation
* **Required Files per Project Component**:
  - **Thin-Pointer `GEMINI.md`**: Linking back to the workspace root rules in `C:\dev\docs\ai\RULES.md`.
  - **Detailed `AI.md`**: Project-specific context (tech stack, key Nx commands, port configurations, and architectural patterns) dynamically generated by analyzing `project.json`, `package.json`, and source code.
  - **Technical `README.md`**: Component overview, quick start, build, and test commands.
  - **`RELEASE_READY.md`** (Applications Only): Production release checklist, build verification, and current release metadata.
