# Learning System Integration for Monorepo Agents

> **Schema verified against live `D:\databases\agent_learning.db` on 2026-07-07** by running
> `sqlite3 D:\databases\agent_learning.db ".schema <table>"` for every table referenced below.
> If the schema drifts, re-run `.schema <table>` before trusting this doc again —
> `DB_INVENTORY.md` on `D:\databases\` is the authoritative source of truth, not this file.
>
> **Canonical write path**: the intended tool for contributing a pattern is memory-mcp's
> `memory_learning_write_pattern` (not currently exposed as a callable tool in Claude Code
> sessions). Until it is exposed, the fallback is a direct `sqlite3` INSERT into
> `success_patterns` as shown below.

Use this skill when automating monorepo tasks to leverage collective knowledge and prevent repeating mistakes.

## Core Workflow (MANDATORY Before ANY Action)

### 1. Query for Proven Patterns

Before implementing any task, check if successful approaches exist. `success_patterns` is the
canonical table for this — it has the `confidence_score` field the original 0.8 threshold maps to:

```sql
-- Find proven patterns for your task type (success_patterns is the canonical source)
SELECT pattern_type, description, confidence_score, last_used
FROM success_patterns
WHERE pattern_type = 'your_task_type'
  AND confidence_score >= 0.8
ORDER BY confidence_score DESC, last_used DESC
LIMIT 5;
```

`task_patterns` is a simpler, frequency-counted companion table — it has no rate/score column,
only a raw `frequency` counter, so use it when you just want "what's been tried most often":

```sql
-- Find frequently-recommended approaches for your task type
SELECT pattern_type, recommended_approach, frequency, created_at
FROM task_patterns
WHERE pattern_type = 'your_task_type'
ORDER BY frequency DESC, created_at DESC
LIMIT 5;
```

**Task types**: `quality-check`, `dependency-update`, `mobile-build`, `desktop-release`, `test-execution`, `documentation-sync`, `cache-optimization`, `dead-code-detection`

### 2. Check for Known Mistakes

Prevent repeating errors by checking the mistake database. `agent_mistakes` has no
`times_occurred` counter — repeated occurrences are tracked as separate rows, so filter on
`resolved = 0` (still an open issue) instead:

```sql
-- Check if this action has failed before (still unresolved)
SELECT mistake_type, description, prevention_strategy, impact_severity
FROM agent_mistakes
WHERE context_when_occurred LIKE '%your_context%'
  AND resolved = 0
ORDER BY identified_at DESC
LIMIT 10;
```

**If found**: Apply prevention strategy BEFORE executing action.

### 3. Log Your Execution

Record every tool use for pattern recognition. The live `agent_executions` table's primary key
is `execution_id` (TEXT, not an autoincrement `id`), so generate an id up front and reuse it for
the follow-up UPDATE. There is no `input_params`/`output_data` pair — use the single `metadata`
JSON column for both:

```sql
-- Log execution start (execution_id generated by the caller, e.g. a UUID)
INSERT INTO agent_executions (
  execution_id, agent_id, agent_name, task_type, context,
  metadata, started_at
) VALUES (
  'exec-20260707-0001', 'your-agent-name', 'your-agent-name',
  'quality-check', 'quality check',
  '{"cmd": "pnpm run lint"}', datetime('now')
);

-- Log execution result (matched on the same execution_id)
UPDATE agent_executions
SET completed_at = datetime('now'),
    success = 1, -- or 0 if failed
    execution_time_ms = 1250,
    error_message = NULL -- or error details if failed
WHERE execution_id = 'exec-20260707-0001';
```

Note: Agent tool invocations are already recorded automatically by the
`PostToolUse(Agent)` hook (`.claude/hooks/record-agent-execution.ps1`, see
`.claude/rules/memory-system.md`). Only do a manual INSERT/UPDATE like the above for
bespoke tool tracking outside that hook (e.g. logging a raw Bash quality check).

### 4. Contribute Knowledge (If Successful)

After successful execution (confidence_score >= 0.8), contribute to the knowledge base.
`success_patterns` is the canonical table for a general, non-file-specific pattern:

```sql
-- Add proven pattern (success_patterns is the canonical table for this)
INSERT INTO success_patterns (
  pattern_type, description, confidence_score, metadata
) VALUES (
  'quality-check',
  'Run lint with --fix, then typecheck, then build. Parallel where possible.',
  0.95,
  '{"source": "Incremental Quality Check"}'
);
```

`code_patterns` exists too, but it is shaped for a real, file-anchored code snippet, not a
generic "pattern with a success rate" — `file_path`, `name`, `code_snippet`, and `language` are
all `NOT NULL`, and there is no `success_rate`/`use_case` column. Only use it when you have an
actual file the snippet lives in or was extracted from:

```sql
-- Add a reusable code snippet tied to a real file (code_patterns requires file_path)
INSERT INTO code_patterns (
  pattern_type, name, code_snippet, file_path, language,
  tags, created_at
) VALUES (
  'command', 'Nx Affected Test',
  'pnpm nx affected:test --parallel=3 --max-parallel=3',
  'scripts/quality-affected.ps1', 'bash',
  'nx,testing,parallel', strftime('%s', 'now')
);
```

### 5. Record Mistakes (If Failed)

If execution fails, record for future prevention using the real `agent_mistakes` columns.
There is no `times_occurred` counter — insert a new row per occurrence rather than
incrementing a field, and set `resolved = 0` while it's still an open problem:

```sql
-- Record mistake
INSERT INTO agent_mistakes (
  mistake_type, mistake_category, description,
  context_when_occurred, impact_severity,
  prevention_strategy, identified_at, resolved
) VALUES (
  'build-failure', 'mobile-build',
  'Build failed due to missing versionCode increment',
  'Android build',
  'medium',
  'Always increment versionCode before Android builds to force cache clear',
  datetime('now'), 0
);
```

## Database Schema Reference

### Tables

**agent_executions** - Complete tool usage history (PK is `execution_id`, a TEXT you generate,
not an autoincrement `id`)

- `execution_id` - Caller-generated unique id (TEXT PRIMARY KEY)
- `agent_id` / `agent_name` - Which agent executed (`agent_name` defaults to `'gravity-claw'`)
- `task_type` - Category of task performed
- `context` - What task was being performed
- `tools_used` - Tools invoked during the execution
- `metadata` - JSON blob for parameters and/or results (no separate input/output columns)
- `success` - 1/TRUE for success, 0/FALSE for failure
- `execution_time_ms` - Performance metric
- `error_message` - Failure details
- `started_at` / `completed_at` - ISO 8601 timestamps

**task_patterns** - High-level, frequency-counted task execution strategies (no rate/score field)

- `pattern_type` - Category (quality-check, mobile-build, etc.) — doubles as the task type
- `frequency` - Raw counter, how often this approach has been recommended/used
- `recommended_approach` - How to execute successfully
- `created_at` - Unix epoch seconds

**success_patterns** - The canonical "proven pattern with a confidence score" table

- `pattern_type` - Category
- `description` - How to execute successfully
- `confidence_score` - 0.0 to 1.0, >= 0.8 is proven
- `frequency` - Times this pattern has been observed
- `last_used` - Timestamp of last successful use
- `metadata` - JSON blob for extra context

**code_patterns** - Reusable code snippets anchored to a real file (no success rate)

- `pattern_type` - Category
- `name` - Descriptive name
- `code_snippet` - Actual code to execute
- `file_path` - The file the snippet lives in/was extracted from (`NOT NULL`)
- `language` - bash, typescript, python, powershell (`NOT NULL`)
- `imports` / `tags` - Optional metadata
- `usage_count` / `last_used` - Frequency counters
- Unique on `(file_path, name, pattern_type)`

**agent_mistakes** - Error tracking and prevention (no `times_occurred` counter)

- `mistake_type` / `mistake_category` - Classification of the error
- `description` - What went wrong
- `root_cause_analysis` - Why it happened
- `context_when_occurred` - What was being attempted
- `impact_severity` - e.g. low/medium/high/critical
- `prevention_strategy` - How to avoid in future
- `identified_at` - When first detected (TEXT timestamp)
- `resolved` - 0/1, whether it's still occurring

**agent_knowledge** - Curated knowledge base (RAG). There is currently no `agent_knowledge_fts`
FTS5 virtual table live in the database — full-text search over this table is not implemented.

- `knowledge_type` - Categorization (not `category`)
- `title` - Knowledge entry title
- `content` - Detailed explanation
- `applicable_tasks` / `applicable_contexts` - When this knowledge applies
- `effectiveness_score` - 0.0 to 1.0, for ranking (not `relevance_score`)
- `usage_count` / `last_used` - Usage tracking (not `times_accessed`/`last_accessed`)
- `created_at` - Timestamp

## Integration with Agents

All agents MUST follow this workflow:

```
1. Query success_patterns (proven approaches, confidence_score >= 0.8)
2. Query agent_mistakes (prevention strategies, resolved = 0)
3. Apply prevention strategies if mistakes found
4. Execute task with proven pattern if available
5. Log execution to agent_executions
6. If success: Contribute to success_patterns (and code_patterns if file-anchored)
7. If failure: Record to agent_mistakes
8. Update confidence_score / frequency metrics
```

## Example: Pre-commit Quality Gate Agent

```typescript
// 1. Query for proven quality check pattern
const proven = await queryDB(`
  SELECT description FROM success_patterns
  WHERE pattern_type = 'quality-check' AND confidence_score >= 0.8
  ORDER BY confidence_score DESC LIMIT 1
`);

// 2. Check for known, still-unresolved mistakes
const mistakes = await queryDB(`
  SELECT prevention_strategy FROM agent_mistakes
  WHERE context_when_occurred LIKE '%quality%' AND resolved = 0
`);

// 3. Apply prevention strategies
if (mistakes.includes('Always run lint --fix first')) {
  await runLintFix();
}

// 4. Execute with proven pattern
const result = await executeQualityCheck(proven.description);

// 5. Log execution
await logExecution({
  execution_id: crypto.randomUUID(),
  agent_name: 'pre-commit-quality-gate',
  task_type: 'quality-check',
  context: 'quality check before commit',
  success: result.exitCode === 0,
  execution_time_ms: result.duration,
});

// 6. Contribute knowledge if successful
if (result.exitCode === 0) {
  await updateConfidenceScore('quality-check', 0.95);
}

// 7. Record mistake if failed
if (result.exitCode !== 0) {
  await recordMistake({
    context_when_occurred: 'quality check',
    description: result.error,
    prevention_strategy: 'Run tests with --runInBand to avoid race conditions',
    impact_severity: 'medium',
  });
}
```

## Performance Considerations

- **Query first, act second** - Always check learning database before executing
- **Log asynchronously** - Don't block on logging (use background writes)
- **Cache frequent queries** - Cache `success_patterns`/`task_patterns` lookups for 5 minutes
- **Update metrics incrementally** - Don't recalculate confidence scores on every execution
- **Archive old mistakes** - There is no `agent_mistakes_archive` table today; if volume grows,
  periodically `DELETE` rows where `resolved = 1` after reviewing, rather than assuming an
  archive table exists

## Success Metrics

Track agent performance with these queries:

```sql
-- Agent success rate by task type (agent_name exists on the live table)
SELECT
  agent_name,
  COUNT(*) as total_executions,
  SUM(CASE WHEN success = 1 THEN 1 ELSE 0 END) as successful,
  ROUND(AVG(CASE WHEN success = 1 THEN 1.0 ELSE 0.0 END), 2) as success_rate
FROM agent_executions
WHERE started_at >= datetime('now', '-30 days')
GROUP BY agent_name
ORDER BY success_rate DESC;

-- Most valuable patterns (high confidence, frequently used)
SELECT pattern_type, description, confidence_score, frequency
FROM success_patterns
WHERE last_used >= datetime('now', '-30 days')
ORDER BY confidence_score DESC, frequency DESC
LIMIT 10;

-- Unresolved mistakes to prioritize fixing (no times_occurred counter — rank by severity)
SELECT context_when_occurred, description, prevention_strategy, impact_severity
FROM agent_mistakes
WHERE resolved = 0
ORDER BY
  CASE impact_severity
    WHEN 'critical' THEN 4
    WHEN 'high' THEN 3
    WHEN 'medium' THEN 2
    ELSE 1
  END DESC,
  identified_at DESC
LIMIT 10;
```
